## PHASE 1 — Multi-core VPN engine (Xray first)

**Problem:** the app currently uses only sing-box (libbox). My configs are VLESS links carrying modern Xray-only features (Reality, XTLS-Vision, XHTTP / SplitHTTP with modes and "extra" JSON, VLESS Encryption / mlkem768x25519plus post-quantum, fragment/noise, mux, etc.), which sing-box cannot run correctly. **Xray-core must be the PRIMARY engine, with sing-box as a secondary engine.**

### Requirements

1. **`VpnCore` interface** (`start(config, tunFd)`, `stop()`, stats `Flow`, `urlTest/ping`) with two implementations: `XrayCore` (primary) and `SingBoxCore` (secondary). Add a `CoreSelector` that chooses automatically:
   - Default -> Xray.
   - Use Xray for: VLESS/VMess/Trojan/Shadowsocks with xhttp, splithttp, reality, vision, VLESS encryption, httpupgrade, grpc, ws, tcp, kcp.
   - Use sing-box only for protocols Xray can't handle (Hysteria2/TUIC/WireGuard if present) or if the user manually forces it.
   - Settings: "Core: Auto / Xray / sing-box".

2. **Xray integration on Android:** use the latest Xray-core via an open-source gomobile binding (XTLS/libXray or 2dust AndroidLibXrayLite), plus a TUN bridge (hev-socks5-tunnel or tun2socks) fed by the VpnService file descriptor. Handle the full lifecycle, DNS, IPv6, routing (bypass LAN / private IPs), per-app split tunneling, MTU, and foreground notification. Use ABI splits to keep APK size reasonable.

3. **`XrayConfigBuilder`:** generate a full valid Xray JSON (inbounds, outbounds, dns, routing, policy, stats, log) from a parsed share link. Parse EVERY param of `vless://` links correctly: `type, security, encryption, flow, sni, fp, pbk, sid, spx, pqv, alpn, allowInsecure, path, host, mode, extra` (URL-decoded JSON for xhttp), `serviceName, authority, headerType, seed, packetEncoding`, etc. Same for `vmess://` (base64 JSON), `trojan://`, `ss://`.

4. **IMPORTANT — check my PasarGuard API docs for subscription formats.** If the panel exposes an Xray-JSON subscription (v2ray-json / xray format) in addition to plain links, PREFER it as the source of truth (it contains the exact config the panel intends) and use link parsing only as a fallback. Make this a configurable strategy.

5. Keep the link parser + `SingBoxConfigBuilder` for the secondary engine. Share one `ProxyLinkParser` model between both builders.

6. **Live speed/traffic stats** from Xray's stats API (or the binding's equivalent), **real latency test** (through-core URL test, not only TCP ping), and clear error messages when a config uses a feature the chosen core doesn't support.

7. **Unit tests** for the parsers/builders using sample links:
   - VLESS Reality + Vision
   - VLESS XHTTP
   - VLESS with encryption param
   - VMess ws + tls
   - Trojan grpc
   - Shadowsocks

   Explain exactly which Xray-core version/binding you used and how to update it.
