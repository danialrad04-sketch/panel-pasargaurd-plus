# سرویس پرداخت پاسارگارد پلاس

سایت پرداخت در مسیر `/` و پنل مدیریت در `/admin` است. سایت و اپ اندروید از API مشترک استفاده می‌کنند. سرویس با مسیر `/sub/{token}/info` در پنل پاسارگارد، اشتراک و دسترسی به سفارش‌ها را بررسی می‌کند.

## نصب روی سرور

قبل از اجرا، DNS دامنهٔ پرداخت را به این سرور وصل کنید و دسترسی عمومی به پورت‌های ۸۰ و ۴۴۳ را بررسی کنید. پلن‌ها و قیمت‌ها از `android-client/app/src/main/assets/plans_config.json` خوانده می‌شوند.

روی سرور، از یک نسخهٔ مخزن که مدیر سرور به آن دسترسی نوشتن دارد اجرا کنید.

```bash
git clone --branch codex/pasarguard-billing --single-branch \
  https://github.com/danialrad04-sketch/panel-pasargaurd-plus.git
cd panel-pasargaurd-plus
sudo bash billing-service/install.sh \
  --domain pay.esfahanmarket.shop \
  --panel-url https://got.esfahanmarket.shop:8443 \
  --sms-format blu --show-credentials
```

- بعد از نصب اول، شماره کارت، نام دارنده و بانک را از «کارت مقصد» در `/admin` وارد کنید. ایجاد سفارش تا ثبت کارت غیرفعال است. اگر پیامک بانک شناسهٔ حساب دارد، با حالت پیش‌فرض `account` نصب کنید و برای فعال کردن تأیید خودکار، `SMS_ACCOUNT` را در `.env` تنظیم کنید. برای تغییر یک نصب موجود به بلو، مقدار `SMS_FORMAT` را در همان فایل به `blu` تغییر دهید و نصب‌کننده را با `--update` اجرا کنید.
- اسکریپت کلیدهای سرویس، وبهوک و رمز ادمین را تولید می‌کند و در `billing-service/.env` با دسترسی `600` نگه می‌دارد. برای دیدن فقط رمز ادمین و کلید وبهوک در ترمینال خصوصی، دستور را با `--show-credentials` اجرا کنید. نام کاربری پنل `admin` است.
- حالت پیش‌فرض `--tls auto` روی پورت‌های آزاد از Caddy و HTTPS خودکار استفاده می‌کند. روی Nginx فعال میزبان، یک فایل اختصاصی در `conf.d` می‌سازد و Certbot را برای صدور و تمدید گواهی به‌کار می‌گیرد. برای پراکسی‌های دیگر، `--tls external` بک‌اند را روی `http://127.0.0.1:8087` بالا می‌آورد و مسیر HTTPS را باید در همان پراکسی تنظیم کنید. برای دسترسی اینترنتی، پراکسی باید فقط درخواست‌های دامنهٔ پرداخت را به این آدرس بفرستد.
- روی Ubuntu/Debian، نصب‌کننده بسته‌های در دسترس توزیع را برای پیش‌نیازهای غایب نصب می‌کند. Docker و افزونهٔ Compose v2 با قابلیت `up --wait` لازم‌اند. در اجرای دوباره، فایل تنظیمات، کلیدها و داده‌های سفارش حفظ می‌شوند. همراه نسخهٔ پشتیبان SQLite، فایل `.env` را هم در محل امن نگه دارید.
- برای بررسی وضعیت و لاگ بک‌اند، `sudo docker compose -p billing-service -f billing-service/compose.yml ps` و `sudo docker compose -p billing-service -f billing-service/compose.yml logs --tail=100 billing` را اجرا کنید.
- دستور `sudo bash billing-service/install.sh --status` کانتینرها و پاسخ سلامت سرویس روی لوپ‌بک و HTTPS را بررسی می‌کند.

## به‌روزرسانی نصب فعلی

```bash
git pull --ff-only &&
sudo bash billing-service/install.sh --update
```

به‌روزرسانی از دیتابیس، پراکسی HTTPS و کلیدهای موجود استفاده می‌کند. اگر فایل `.env` در پوشهٔ فعلی نباشد، تنظیمات از کانتینر فعلی سرویس بازیابی می‌شود. برای دیدن وضعیت بدون به‌روزرسانی، گزینهٔ `--status` را اجرا کنید.

## داشبورد مدیریت

در `/admin/login` با نام کاربری `admin` و همان رمز `ADMIN_PASSWORD` نصب فعلی وارد شوید. نشست مدیر پس از ۸ ساعت یا با خروج از پنل پایان می‌یابد. محدودیت تلاش ورود بر پایهٔ نشانی دریافت‌شده از پراکسی است. پراکسی خارجی باید نشانی واقعی اتصال را در آخرین مقدار `X-Forwarded-For` بنویسد و مسیر داخلی سرویس را خصوصی نگه دارد.

در «فعالیت‌ها» می‌توانید ورود و خروج، تصمیم‌های پرداخت و تغییرات تنظیمات را ببینید. خروجی CSV در «سفارش‌ها» فیلترهای فعال را رعایت می‌کند و تا ۱۰ هزار سفارش را با شناسه، مبلغ، وضعیت، زمان ثبت UTC و وجود تصویر فیش دانلود می‌کند.

فونت‌های وزیرمتن و استعداد از خود سرویس بارگیری می‌شوند. فایل‌های مجوز آن‌ها در `web/fonts/` قرار دارند. [وزیرمتن](https://github.com/rastikerdar/vazirmatn) · [استعداد](https://github.com/aminabedi68/Estedad)

در مسیر `/admin` نمودار مبلغ و تعداد سفارش‌های تأییدشده را در بازهٔ ۷ یا ۳۰ روز، صف بررسی رسیدها و واریزهای تطبیق‌داده‌شده یا بدون سفارش می‌بینید. فیلتر «دارای عکس فیش» سفارش‌های دارای تصویر را نشان می‌دهد. بخش «کارت مقصد» شماره، نام دارنده و نام بانک را برای سفارش‌های بعدی وب و اندروید در دیتابیس ثبت می‌کند. کارت سفارش‌های قبلی از زمان ثبت سفارش حفظ می‌شود. تغییر کارت در پنل برای کارت جایگزین همان حساب متصل به فرستندهٔ پیامک است. سابقهٔ تغییرات فقط چهار رقم آخر کارت قبلی و جدید را نشان می‌دهد.

برای بازتولید فایل CSS ابزارهای پنل از داخل `billing-service` دستور `npm ci && npm run build:admin` را اجرا کنید. CSS تولیدشده با Tailwind CSS v4 همراه سرویس نصب می‌شود.

## وصل کردن تأیید خودکار

اپ می‌تواند عکس فیش را همراه شمارهٔ پیگیری یا به‌تنهایی برای سفارش ارسال کند. عکس در «سفارش‌ها ← جزئیات سفارش» پنل مدیریت قابل مشاهده است. پیوست کردن عکس به سفارش تأییدشده، وضعیت آن را تغییر نمی‌دهد. برای پراکسی خارجی، سقف بدنهٔ درخواست را برای مسیر ثبت رسید دست‌کم روی ۷۶۸ کیلوبایت بگذارید. نصب‌کننده سقف پراکسی‌های Caddy و Nginx خودش را هنگام به‌روزرسانی تنظیم می‌کند.

ارسال‌کننده روی گوشی دریافت‌کنندهٔ پیامک بانک باید پیام‌های فرستندهٔ بانک برای حساب مقصد را با این مشخصات ارسال کند. کلید را از تنظیمات خصوصی همین نصب بخوانید.

- روش و مسیر درخواست `POST https://pay.esfahanmarket.shop/web/shop/payments/card-deposit/webhook`
- هدر `X-Webhook-Secret` با مقدار `SMS_WEBHOOK_SECRET`
- بدنهٔ سازگار با `myproject` با قالب `{"key":"{msg}","time":"{time}"}`

حالت پیش‌فرض `account` پیامک واریز ریالی با خط «حساب» یا قالب پاسارگاد با خط `Save:` را می‌پذیرد. حالت `blu` پیامک «واریز پول» بلو را با مبلغ و زمان شمسی داخل پیامک تطبیق می‌دهد. چون این قالب شمارهٔ حساب ندارد، فرستنده باید فقط پیامک‌های رسمی بانک برای همان یک حساب بلو را به این وبهوک بفرستد. یک واریز آزمایشی با مبلغ دقیق نمایش‌داده‌شده در سایت یا اپ انجام دهید و تأیید آن را در هر دو بررسی کنید. اگر دو سرویس مستقل هم‌زمان سفارش کارت‌به‌کارت می‌پذیرند، برای هر سرویس حساب مقصد جداگانه تنظیم کنید تا سفارش‌های هم‌مبلغ تداخل نکنند.

واریز با مبلغ رزروشده، حساب مقصد و مهلت سفارش تطبیق داده می‌شود. برای بررسی دستی، کاربر شمارهٔ پیگیری ثبت می‌کند و ادمین پس از تطبیق واریز تصمیم می‌گیرد. تمدید یا افزودن حجم پس از تأیید مالی در پنل VPN انجام می‌شود. مبلغ رزروشده دوباره تخصیص داده نمی‌شود و هر پلن در بازهٔ قیمت خودش تا هزار مبلغ رزرو دارد.

## ساخت APK برای همین دامنه

### خرید بدون اشتراک در اندروید

۱. در داشبورد پاسارگارد، از بخش **API Keys** کلیدی با دسترسی خواندن گروه‌ها و خواندن و ساخت کاربران ایجاد کنید.
۲. در پنل پرداخت، **کارت مقصد ← ساخت خودکار اشتراک** را باز کنید. کلید را در همان فرم وارد کنید، **دریافت گروه‌های سرور** را بزنید، گروه موردنظر را با اسم انتخاب و اتصال را ذخیره کنید.
۳. در نسخهٔ جدید اپ، **خرید اشتراک جدید** را بزنید. سفارش بعد از تأیید واریز در صف ساخت اشتراک قرار می‌گیرد. اپ لینک را از بک‌اند دریافت می‌کند و فقط وقتی کانفیگ قابل استفاده دریافت شد آن را وارد می‌کند. برای ادامه پس از بستن اپ، **پیگیری خرید** را روی همان نصب باز کنید.

کلید API فقط روی سرور پرداخت نگه‌داری می‌شود. صف ساخت و وضعیت فعال‌سازی در SQLite می‌مانند و با راه‌اندازی دوباره قابل ادامه‌اند. هر سفارش پرداخت‌شدهٔ خرید جدید به یک حساب پاسارگارد نگاشت می‌شود. مسیر تمدید اشتراک‌های موجود از تنظیمات قبلی پیروی می‌کند.

### تنظیمات ساخت

در GitHub Actions گردش کار `Build PasarGuard Android VPN APK` را روی شاخهٔ پرداخت اجرا کنید و آدرس‌های پنل و پرداخت را در ورودی‌های `panel_base_url` و `billing_base_url` بگذارید. همین مقادیر را می‌توان به‌ترتیب با متغیرهای `PASARGUARD_BASE_URL` و `PASARGUARD_BILLING_URL` تنظیم کرد. برای انتشار، APK را با کلید انتشار پروژه امضا کنید.

## پلن‌ها، حساب مشتری و کیف پول

پلن‌های اولیه از فایل همراه نصب خوانده می‌شوند. مدیر از «پلن‌ها» قیمت، حجم، مدت، تعداد دستگاه، عنوان و ویژگی‌های فارسی و انگلیسی، نشان‌ها، ترتیب و نمایش را تغییر می‌دهد. یک پلن مخفی برای سفارش تازه قابل استفاده نیست. مبالغ و شرایط سفارش ثبت‌شده بر اساس زمان ثبت همان سفارش می‌مانند.

ورود، ساخت حساب، سفارش‌ها و کیف پول در بخش «حساب کاربری» خود اپ‌ها در دسترس‌اند. ثبت حساب Gmail و بازیابی رمز با کد ایمیلی انجام می‌شوند. برای فعال شدن ارسال واقعی، متغیرهای `CUSTOMER_SMTP_HOST`، `CUSTOMER_SMTP_FROM`، `CUSTOMER_SMTP_PORT` و در صورت نیاز نام کاربری و رمز SMTP را در `.env` سرویس تنظیم کنید و نصب‌کننده را با `--update` اجرا کنید. حساب از رمز مستقل پاسارگارد استفاده می‌کند.

برای اشتراک خریداری‌شده از همین سرویس، لغو با تأیید مشتری شروع می‌شود. سهم زمان باقی‌مانده از مبلغ پرداختی، گرد شده به پایین تا یک تومان، پس از تأیید غیرفعال‌سازی به کیف پول اضافه می‌شود. کلید اتصال پاسارگارد باید دسترسی خواندن و تغییر وضعیت اشتراک‌های ساخته‌شده را داشته باشد. مشتری می‌تواند با موجودی کافی به‌طور کامل از کیف پول پرداخت کند. اشتراک خریداری‌شده در نسخه‌های قبلی اندروید از جزئیات همان سفارش و روی دستگاه خریدار به حساب کاربری منتقل می‌شود. برای تمدید، همان اشتراک را در اپ فعال کنید و پلن بخرید. پس از تأیید پرداخت، مدت و حجم در صف پردازش به همان اشتراک اعمال می‌شوند. کلید اتصال پنل به دسترسی تغییر کاربر نیاز دارد.

## انتشار و به‌روزرسانی اپ‌ها

در «تنظیمات پرداخت ← به‌روزرسانی اپ‌ها» می‌توانید نسخه، شمارهٔ ساخت، شناسهٔ بسته و یادداشت انتشار را ثبت و پیشنهاد نسخه را فعال یا غیرفعال کنید. برای اندروید، معماری را انتخاب و فایل APK را بارگذاری کنید یا از فهرست فایل‌های بارگذاری‌شده انتخاب کنید. پنل آدرس عمومی و SHA-256 را وارد می‌کند. می‌توانید «کپی لینک عمومی» را بزنید و لینک را مستقیم به کاربران بدهید. برای پیشنهاد درون اپ، شمارهٔ ساخت و نسخه را مطابق همان APK وارد کنید، گزینهٔ نمایش را فعال کنید و «ذخیرهٔ نسخه» را بزنید. امکان وارد کردن آدرس HTTPS و هش به‌صورت دستی هم وجود دارد. برای iOS، لینک App Store یا TestFlight را وارد کنید. اپ‌ها در زمان فعال شدن، حداکثر هر شش ساعت بررسی می‌کنند و بررسی دستی هم در بخش اشتراک دارند.

برای انتشار خودکار اندروید روی GitHub Releases، `ANDROID_RELEASE_REPOSITORY=danialrad04-sketch/panel-pasargaurd-plus` را در `.env` تنظیم کنید و هر نسخهٔ امضاشده را از workflow اندروید با گزینهٔ `publish_release` و شمارهٔ ساخت بالاتر منتشر کنید. workflow فایل APKهای هر معماری و هش آن‌ها را در Release قرار می‌دهد. اگر برای اندروید پیشنهادی در پنل ذخیره شده باشد، همان تنظیمات دستی اولویت دارد. دانلود GitHub Releases باید بدون ورود در دسترس باشد.

### تطبیق دستی و لینک دانلود

در «واریزی‌ها»، کنار واریز بدون سفارش «تطبیق دستی» را بزنید. شناسهٔ سفارش را وارد کنید، مبلغ و زمان‌ها را با گردش بانک بررسی کنید و دلیل را بنویسید. پس از ثبت، مبلغ واقعی واریز در سفارش و گزارش ثبت می‌شود و فعال‌سازی وارد همان صف خودکار می‌شود. واریز کمتر از قیمت پایه نیاز به رسیدگی جداگانه دارد.

پیوند `/download/android.apk` روی دامنهٔ پرداخت به نسخهٔ قابل عرضهٔ اندروید هدایت می‌کند. پیش‌فرض ARM64 است. برای دستگاه‌های دیگر مقدار `abi` را در آدرس مشخص کنید. پیوند پس از قابل عرضه کردن نسخه در «تنظیمات ← انتشار برنامه» فعال است.

### پشتیبان‌گیری پایگاه‌داده پیش از استقرار

از ریشهٔ پروژه روی سرور، این دستور یک نسخهٔ سازگار SQLite می‌گیرد و بررسی سلامت نسخهٔ کپی‌شده را پیش از خروجی انجام می‌دهد:

```bash
umask 077
backup="billing-$(date -u +%Y%m%dT%H%M%SZ).sqlite3"
sudo docker compose -p billing-service -f billing-service/compose.yml exec -T billing python - > "$backup" <<'PY'
import os
import sqlite3
import sys
import tempfile
from contextlib import closing
from pathlib import Path

with tempfile.TemporaryDirectory() as directory:
    snapshot = Path(directory) / "billing.sqlite3"
    with closing(sqlite3.connect(Path(os.environ["BILLING_DB"]).as_uri() + "?mode=ro", uri=True)) as source:
        with closing(sqlite3.connect(snapshot)) as target:
            source.backup(target)
            if target.execute("PRAGMA quick_check").fetchall() != [("ok",)]:
                raise RuntimeError("SQLite backup integrity check failed")
    with snapshot.open("rb") as stream:
        while chunk := stream.read(1024 * 1024):
            sys.stdout.buffer.write(chunk)
PY
```

فایل پشتیبان را همراه با نسخهٔ محافظت‌شدهٔ `.env` و فایل‌های بارگذاری‌شده در `/data/apk` نگه دارید. تصویر رسید داخل خود دیتابیس پشتیبان است. قبل از تکیه بر این فایل برای بازیابی، آن را روی یک سرویس آزمایشی جدا باز کنید.
