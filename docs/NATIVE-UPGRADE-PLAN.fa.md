# مسیر ارتقای نیتیو PasarGuard Plus

## تصمیم معماری

درخواست کاربر این است که **خود پاسارگارد ارتقا پیدا کند**؛ نه اینکه یک داشبورد کنترل برای محصولات مستقل دونینو ساخته شود. بنابراین:

1. منبع یکتای کاربر، مدیر، نود، گروه، وضعیت، حجم و اشتراک، مدل فعلی پاسارگارد است.
2. هر قابلیت جدید باید در SQLAlchemy/Alembic، API typed، RolePermissions، OpenAPI/client، lifecycle و رابط پاسارگارد حضور داشته باشد.
3. ابزارهای شبکه با موتور یا worker همان محصول و قرارداد قابل نسخه‌بندی نود اجرا می‌شوند. worker یک جزء سرویس است، نه پنل جدا، دیتابیس جدا یا proxy به API دونینو.
4. حسابداری VPN با کپی‌کردن شمارنده‌های دیتابیس دونینو جایگزین نمی‌شود. هر ledger جدید تعریف واحد، دوره، رزرو، idempotency و رفتار قطع ارتباط خودش را دارد و در نهایت به کاربر بومی متصل می‌شود.
5. موفقیت ساخت تنظیمات، نصب engine، سلامت مسیر و پذیرش کلاینت وضعیت‌های جدا هستند. هیچ‌کدام از روی دیگری حدس زده نمی‌شوند.
6. قالب و تنظیمات فعلی اپراتور حفظ می‌شوند. قابلیت تازه نیازمند migration افزایشی و پذیرش با داده موجود است.

## وضعیت تطبیق قابلیت‌ها

«موجود» برای امکانات پایه، به کد فعلی پاسارگارد اشاره دارد؛ این سند ادعای اجرای همه آنها در شبکه واقعی نمی‌کند.

| قابلیت در پروژه‌های دونینو | وضعیت در این فورک | مرز کار نیتیو بعدی |
|---|---|---|
| کاربر، حجم، انقضا، شروع on-hold، پلن بعدی | پایه بومی پاسارگارد موجود | حفظ رفتار و مدل؛ ساخت کاربر موازی ممنوع |
| مدیر، نقش، API key، محدودیت مالکیت | پایه موجود؛ مجوز DNS به آن افزوده شد | مجوز هر سرویس تازه در همان RolePermissions |
| چند نود، NATS، heartbeat، آمار | پایه بومی موجود | قابلیت تازه باید قرارداد worker و نسخه نود را اعلام کند |
| Xray، VLESS/VMess/Trojan، Shadowsocks و WireGuard | موتورهای بومی موجود | تفاوت‌های دقیق پروتکل/کلاینت باید در runtime همان موتور پذیرفته شوند؛ کپی ماژول هم‌نام لازم نیست |
| پورتال اشتراک، QR و رابط فارسی | قالب پیش‌فرض بازطراحی و DNS در آن یکپارچه شد | بومی‌سازی زبان‌های دیگر صفحه ساب و ادامه طراحی سایر صفحات |
| DNS policy، سهمیه درخواست، دوره، DoH | **نیتیو پیاده‌سازی و آزموده شد** | پذیرش resolver عملیاتی/ظرفیت و شبکه کاربر |
| DNS UDP/TCP/DoT و lease مبدأ | **worker بومی و transport واقعی loopback آزموده شد** | استقرار و پذیرش پورت عمومی، TLS و IPهای کاربر |
| کاتالوگ doctor-dns | snapshot مجاز و ساخت سیاست rewrite نیتیو | کاتالوگ به‌تنهایی نصب relay نیست |
| تونل TCP/UDP بومی بین نودهای رسمی | **SS2022 روی Xray با API، overlay هر نود، apply و آزمون ترافیک واقعی پیاده‌سازی شد** | پایش واقعی و failover افزوده شد؛ پذیرش VPS/IPv6 و حامل‌های بعدی |
| انتشار IP ایران در اشتراک مسیر تونل | **هاست وابسته، تشخیص پورت کاربران، فرم هاست و آزمون API/مرورگر/دو نود پیاده‌سازی شد** | پذیرش IP، گواهی و کلاینت در شبکه واقعی؛ [راهنما](TUNNEL-SUBSCRIPTION-HOSTS.fa.md) |
| Smart DNS relay/exit و failover خروجی | **gateway TCP/UDP، DNS روی نود، خروج از تونل و رزرو بایت نیتیو پیاده‌سازی شد** | پذیرش سرویس مشخص، IP/CGNAT، TLS/ECH و محدودیت UDP؛ [راهنمای عملیات](NATIVE-OPERATIONS.fa.md) |
| مهاجرت حساب‌های doctor-dns | هنوز منتقل نشده | نسخه ورودی مشخص، dry-run، تطبیق شناسه/دوره/حجم، حساب غیرفعال تا پذیرش |
| Paqet | **سورس کامل، compiler بومی، supervisor نود، فرم کامل Linux و آزمون واقعی دو نود TCP/UDP پیاده‌سازی شد** | پذیرش VPS/IPv6 و سنجش کارایی؛ [راهنما](NATIVE-PAQET.fa.md) |
| سایر حامل‌های Donino Tunnel و Continuum | runtime بومی هنوز منتقل نشده | قرارداد قابلیت نود، job پایدار، config compiler، rollback، مالکیت engine و binding به ورودی/host بومی |
| اعتبارنامه مستقل دستگاه و ابطال هر دستگاه | مدل HWID بومی با مدل credential هر دستگاه برابر نیست | کلید پروتکل هر دستگاه، تحویل/لغو به نود و تجمیع مصرف به user_id بدون شمارش تکراری |
| بودجه مشترک چند نود در قطع ارتباط | هنوز منتقل نشده | lease خرج محدود، epoch و گزارش idempotent، بازتخصیص‌ندادن بودجه نامعلوم و enforce آفلاین روی نود |
| OpenVPN با PKI، سهمیه و قطع نشست | هنوز منتقل نشده | adapter موتور در runtime نود، PKI هر دستگاه و CRL، journal مصرف، اتصال به ledger بومی |
| TOTP/MFA و نشست‌های قابل لغو دونینو | پاسارگارد passkey و JWT bound به رمز دارد؛ برابری با TOTP/نشست دونینو ادعا نمی‌شود | مدل مستقل factor/session، رمزگذاری کلید، challenge ضد replay و recovery امن |
| بکاپ و بازیابی | **SQLite سازگار، رمزگذاری، زمان‌بندی، verify و reconcile runtime پیاده‌سازی شد** | adapter موتورهای دیگر و نگهداری offsite اپراتور |

## ترتیب ادامه پیشنهادی بر مبنای وابستگی کد

- Smart DNS: از حساب و سیاست DNS بومی استفاده کند؛ اعتبارنامه خروجی و quota relay نباید به حالت بازِ بدون تأیید تبدیل شوند.
- Tunnel: حامل SS2022 اکنون از قرارداد موجود Xray نود استفاده می‌کند؛ [راهنمای تونل](NATIVE-TUNNELS.fa.md). برای حامل‌های بعدی موتورهای مبدأ به‌صورت engine adapter در همین محصول منتقل شوند. نود همین فورک اکنون Paqet را با قرارداد HTTPS نسخه‌دار و همان CA/API key اجرا می‌کند؛ FRP/OpenVPN هنوز adapter بومی ندارند. راه‌حل میان‌بر، API کنترل پنل مستقل نیست.
- Device و budget: ابتدا قرارداد identity/period/report روی نود، سپس مدل دستگاه در پنل، بعد سهمیه مشترک. افزودن UI پیش از enforce نود، تکمیل قابلیت نیست.
- OpenVPN و قابلیت‌های حساب امنیتی پس از داشتن قرارداد نصب و کلید بررسی شوند؛ بکاپ SQLite اکنون قرارداد رمزگذاری و بازیابی مستقل دارد.

## نقطه ادامه این شاخه

کد bridge قبلی حذف شده؛ ویژگی‌های نیتیو تحویل‌شده DNS و تونل رمز‌شدهٔ TCP/UDP با حامل‌های SS2022 و Paqet بین نودهای همین پنل هستند. راهنمای تونل، محدودیت‌ها و آزمون ترافیک در [این فایل](NATIVE-TUNNELS.fa.md) است. فایل‌های اصلی و راه‌اندازی در [راهنمای نیتیو](DONINO-INTEGRATION.fa.md) آمده‌اند. شواهد شامل migration با حفظ حساب قبلی، quota هم‌زمان، بسته‌شدن دوره، لغو credential/IP، RBAC، سوکت واقعی UDP/TCP/DoT، upstream و TCP fallback و جریان مرورگر متصل به API واقعی است.

این سند یک checkpoint وضعیت است، نه تأیید تکمیل تمام فورک. هیچ VPS، دامنه یا فایروال کاربر در این مرحله تغییر نکرده است.


## پذیرش عملیاتی و تکمیل قابلیت‌های باقی‌مانده

مرحلهٔ عملیات اکنون شامل پایش واقعی حامل، failover با سنجش پس از جابه‌جایی و بازگردانی، SmartDNS مجاز TCP/UDP، DNS روی نود ایران، سهمیهٔ بایتی مستقل، بکاپ رمز‌شده و بازیابی با تطبیق revision نود است. آزمون NATS سه‌سرور و دو worker نیز قطع اتصال، پیام ازدست‌رفته و KV قدیمی را پوشش می‌دهد. [راهنمای عملیات](NATIVE-OPERATIONS.fa.md) و [شواهد تست](NATIVE-VALIDATION.fa.md) مرجع این مرحله هستند.

کار باقی‌مانده برای بهره‌برداری هر نصب: پذیرش IP، TLS، بازی/سرویس و ISP واقعی، ظرفیت، reboot و مانور بازیابی. سایر حامل‌ها، اعتبارنامهٔ مستقل دستگاه، بودجهٔ آفلاین VPN و OpenVPN طبق جدول به توسعهٔ جدا نیاز دارند. این قابلیت‌ها به‌عنوان تحویل‌شده اعلام نمی‌شوند.

## تکمیل مسیر نصب و تست

راهنمای اجرایی یکپارچه در [TESTING-START.fa.md](TESTING-START.fa.md) اضافه شده است. نواقص زیر در این مرحله اصلاح شدند:

| مورد | نتیجه |
|---|---|
| وابستگی نصب Docker به dashboard/build محلی | ساخت frontend داخل image از package.json و bun.lock همین فورک |
| دیتابیس پیش‌فرض داخل لایهٔ موقت کانتینر | مسیر پایدار Compose برای API و worker DNS؛ حفظ URL صریح نصب موجود |
| نبود resolver همراه DNS | Unbound اختیاری، محلی و دارای root anchor؛ پروفایل DNS و volume مستقل |
| آماده‌سازی دستی و خطاپذیر هویت نود جدید | ابزار تولید CA/IP SAN و UUID مستقل، فایل‌های خصوصی و عدم بازنویسی هویت موجود |
| ثبت دستی چندین فیلد حساس نود | واردکردن JSON خصوصی در فرم، بدون ثبت خودکار؛ حفظ دادهٔ واردشده هنگام دریافت دیرهنگام فهرست هسته‌ها |
| گم‌شدن کلیک افزودن نود در بارگذاری اولیه | درخواست پایدار در context مسیر، با regression مرورگر و تأخیر عمدی chunk |
| نبود تشخیص یکپارچه پیش از تست تونل | endpoint مالک و دیالوگ بررسی topology/پورت/lease/revision، listener و کنترل/پردازش Paqet با مهلت محدود |

بررسی آمادگی، جایگزین عبور واقعی ترافیک یا مجوز انتشار خودکار هاست نیست. وضعیت کنترل نود در نتیجه به‌عنوان آخرین وضعیت ثبت‌شده مشخص می‌شود؛ probe افزونهٔ Paqet با TLS معتبر اجرا می‌شود. نتیجهٔ runtime ناموفق مانع تشخیص آمادگی انتشار است، اما اعمال مجدد برای تعمیر مسیر را منع نمی‌کند. پذیرش روی VPS و بازی/ISP واقعی همچنان لازم است.
