# PasarGuard Plus — ارتقای نیتیو بر پایه قابلیت‌های دونینو

هدف این فورک، ارتقای معماری خود پاسارگارد است. کنترل Donino Panel یا Donino Tunnel مستقل از داخل پاسارگارد هدف نیست. نمونه bridge اولیه و تب کنترل‌کننده از این شاخه حذف شده‌اند. به نصب پنل مستقل، socket کنترل دونینو، جفت‌سازی یا دیتابیس دوم نیازی نیست.

## قابلیت نیتیو تحویل‌شده: خدمات DNS

- حساب DNS به `users.id` فعلی متصل است؛ کاربر VPN جدید یا نسخه دوم کاربر ساخته نمی‌شود. حذف تکی، گروهی یا خودکار کاربر، داده‌های وابسته DNS را هم حذف می‌کند. حساب DNS به‌تنهایی قابل حذف است و حذف آن کاربر VPN را پاک نمی‌کند.
- سیاست دامنه با قواعد allow/block/rewrite، تطبیق suffix دقیق، اولویت طولانی‌ترین suffix، قواعد IPv4/IPv6، سیاست روی alias/CNAME و revision قابل ویرایش. API برای جلوگیری از بازنویسی تغییرات هم‌زمان، expected_revision می‌گیرد.
- حسابداری مستقل **تعداد درخواست DNS**، بایت پرسش/پاسخ، خطا و پاسخ مسدود، سهمیه درخواست و محدودیت QPS در همان دیتابیس پاسارگارد. سهمیه DNS از حجم VPN کم نمی‌شود. وضعیت active، انقضا، پایان حجم و سیاست غیرفعال‌شدن مدیر در خود پاسارگارد رعایت می‌شوند؛ کاربر on-hold باید ابتدا طبق چرخه عادی پاسارگارد فعال شود.
- رزرو سهمیه در transaction، قفل سطر حساب در PostgreSQL/MySQL و BEGIN IMMEDIATE در SQLite، بدون نگه‌داشتن قفل DB هنگام تماس resolver. درخواست ناموفق upstream نیز از سهمیه رزروشده استفاده کرده است؛ رد پیش از رزرو مصرفی ندارد. QPS یک پنجره ثابت یک‌ثانیه‌ای و مشترک بین workerها است.
- بازنشانی، دوره قبلی را می‌بندد و دوره تازه می‌سازد. پاسخ درخواست درحال‌اجرا به همان دوره‌ای ثبت می‌شود که درخواست در آن رزرو شده؛ بستن دوره، تاریخچه را صفر نمی‌کند. بازنشانی مصرف VPN، شمارنده DNS را عوض نمی‌کند.
- اعتبارنامه مستقل DNS با HMAC کلید امضای پاسارگارد و nonce هر حساب. raw token در دیتابیس ذخیره نمی‌شود؛ hash قابل جستجو و nonce ذخیره می‌شوند. نمایش یا چرخش اعتبارنامه مجوز جدا می‌خواهد. چرخش DNS، لینک قبلی و leaseهای IP آن حساب را باطل می‌کند. درخواست رزروشده پیش از لغو ممکن است تکمیل شود. تغییر کلید اصلی JWT امکان بازتولید لینک قبلی را از بین می‌برد؛ اعتبارنامه‌های DNS صادرشده تا چرخش خود DNS همچنان با hash ذخیره‌شده معتبرند. برای انتشار لینک تازه یا لغو قبلی، اعتبارنامه DNS را بچرخانید.
- DoH واقعی در API خود پنل: GET/POST طبق RFC 8484، با bearer credential یا مسیر خصوصی سازگار با کلاینت‌ها. پاسخ no-store است؛ اعتبارنامه URL در logger داخلی uvicorn.access پوشانده می‌شود. لاگ reverse proxy باید همین مسیر را redact کند یا access log آن location خاموش باشد.
- worker اختیاری **همین ریپازیتوری** برای UDP، TCP و DoT، با همان سیاست، حساب و سهمیه؛ حداکثر سه lease IP در هر حساب، TTL محدود، تبدیل IPv4-mapped IPv6 به هویت یکسان و جلوگیری از تخصیص هم‌زمان یک IP به دو حساب. دسترسی UDP/TCP/DoT به IP مبدأ وابسته است و IP مشترک NAT بین دو حساب قابل تفکیک نیست؛ DoH credential این وابستگی را ندارد.
- کاتالوگ ۴۲ سرویس، ۴۸ گروه و ۵۰۵ دامنه، با hash و مجوز منبع. ساخت سیاست از گروه‌های منتخب و IPهای relay خارجی اپراتور فراهم است. **کاتالوگ، relay یا خروجی Smart DNS نصب نمی‌کند.** این بخش تنها سیاست DNS rewrite می‌سازد؛ صحت عبور ترافیک، بازی یا ISP از آن نتیجه نمی‌شود.
- مجوزهای `dns.read/create/update/delete/reset_usage/rotate_token` با scope خود/همه در RolePermissions، نقش‌ها و API keyهای خود پاسارگارد. مدیریت سیاست‌های اشتراکی و گزارش audit فقط برای مالک است. نقش‌های غیرمالک بدون اعطای صریح، مجوز جدید نمی‌گیرند؛ نقش مالک طبق رفتار بومی پاسارگارد دسترسی کامل دارد.
- رابط یکپارچه در `/dashboard/#/dns`: حساب‌ها، جستجو و صفحه‌بندی، سهمیه، تاریخچه دوره، ویرایش سیاست، انتخاب کاتالوگ، IPها، چرخش اعتبارنامه و audit. پوسته، زبان، کامپوننت‌ها و احراز هویت همان داشبورد پاسارگاردند.
- صفحه ساب و `/<SUBSCRIPTION_PATH>/{token}/dns` از هویت اشتراک موجود برای نمایش مشخصات DNS همان کاربر استفاده می‌کنند. اطلاعات کاربر دیگر یا raw nonce/hash نمایش داده نمی‌شود. DNS در کپی گروهی لینک‌های VPN وارد نمی‌شود.

سرویس از resolver اعتبارسنج محلی مانند Unbound روی `127.0.0.1:5335` استفاده می‌کند. recursion و DNSSEC به resolver سپرده شده‌اند؛ AD پاسخ synthetic پاک می‌شود. نام دامنه‌های درخواست‌شده در دیتابیس یا audit ثبت نمی‌شود. cache حافظه‌ای محدود به policy/revision و مشخصات پرسش است؛ میان سیاست‌ها اشتراک ندارد. upstream دلخواه از API کاربر پذیرفته نمی‌شود.

## راه‌اندازی روی نصب موجود

از همان محیط و دیتابیس نصب پاسارگارد استفاده کنید. پیش از migration از دیتابیس نصب خود پشتیبان بگیرید؛ دستورات زیر خودشان VPS یا فایروال را تغییر نمی‌دهند:

```sh
uv sync
uv run alembic upgrade head
```

مقادیر `.env` یا محیط سرویس API:

```dotenv
DNS_ENABLED=true
DNS_UPSTREAM=127.0.0.1
DNS_UPSTREAM_PORT=5335
# اختیاری برای دامنه عمومی متفاوت:
# DNS_PUBLIC_URL=https://dns.example.com/dns-query
DNS_LISTEN_ADDRESSES=["127.0.0.1"]
DNS_PORT=5353
```

اگر دامنه ساب یا پیشوند reverse proxy با API تفاوت دارد، `DNS_PUBLIC_URL` را به آدرس عمومی HTTPS تنظیم کنید تا لینک ساخته‌شده در پنل و ساب درست باشد.

برای DoH، اجرای مجدد سرویس API کافی است؛ HTTPS موجود پنل باید برقرار باشد و Unbound باید روی upstream آماده باشد. تنظیم enabled، ادعای آمادگی upstream نیست. برای DNS عادی و DoT، worker بومی را با همان WorkingDirectory و EnvironmentFile پنل اجرا کنید:

```sh
uv run python -m app.dns.worker
```

نمونه‌های Unbound و systemd در [deploy/native-dns](../deploy/native-dns) هستند و قبل از استفاده به تطبیق مسیر، نام کاربر سرویس و مجوز فایل‌های نصب خود نیاز دارند. برای گوش‌دادن روی IP عمومی یا پورت ۵۳ باید آدرس/پورت و دسترسی سیستم‌عامل را صریحاً تنظیم کنید. در معماری چند سرویس نیز worker باید به **همان دیتابیس مشترک** دسترسی داشته باشد؛ دیتابیس محلی جدا نسازید.

DoT اختیاری:

```dotenv
DNS_DOT_PORT=853
DNS_TLS_CERTFILE=/path/to/fullchain.pem
DNS_TLS_KEYFILE=/path/to/privkey.pem
```

ابتدا یک سیاست بسازید، سپس برای کاربر فعلی حساب DNS ایجاد کنید. از «نمایش آدرس خصوصی DoH» یا صفحه ساب کاربر، آدرس را بگیرید. برای UDP/TCP/DoT، IP واقعی مبدأ کاربر را با مدت محدود ثبت کنید. فقط ثبت تنظیمات کافی نیست؛ resolver و ورودی شبکه باید در محیط عملیاتی بررسی شوند.

## صفحه ساب

قالب پیش‌فرض، فارسی RTL، موبایل، تم روشن/تیره، نمای حجم و اعتبار، on-hold، جستجوی اتصال‌ها، کپی تکی/گروهی و QR محلی دارد. قالب سفارشی اپراتور همچنان اولویت دارد. اطلاعات DNS فقط وقتی حساب همان کاربر وجود دارد نمایش داده می‌شود. تصاویر قبلی ساب با داده آزمایشی و تصویر سرویس بومی در [images](images) قرار دارند.

## محدوده باقی‌مانده برای برابری کامل

این تغییر **ارتقای کامل همه امکانات دونینو نیست**. [ماتریس ارتقای نیتیو](NATIVE-UPGRADE-PLAN.fa.md) مرجع وضعیت است. موتورهای تونل، relay/exit واقعی Smart DNS، OpenVPN، مدل دستگاه با اعتبارنامه مستقل و بودجه مشترک چند نود هنوز به معماری پاسارگارد منتقل نشده‌اند. اضافه‌کردن دکمه یا جدول برای قابلیت بدون runtime، تحویل آن محسوب نمی‌شود. API نود فعلی پاسارگارد فقط موتورهای پشتیبانی‌شده خودش را اجرا می‌کند؛ موتور تازه به ارتقای قرارداد و runtime نود هم نیاز دارد.

## اعتبارسنجی

```sh
uv sync --group dev
uv run pytest tests/test_native_dns.py tests/test_native_dns_resolver.py tests/test_donino_subscription_template.py tests/test_app_factory.py -q
cd dashboard
npm run typecheck
npm run build
# در ترمینال دیگر: npm run dev -- --port 4173
node scripts/test-native-dns-ui.mjs
```

آزمون مرورگر یک API واقعی با دیتابیس SQLite موقت می‌سازد و هیچ سرور، حساب یا اعتبارنامه نصب‌شده کاربر را مصرف نمی‌کند. آزمون‌های transport از سوکت‌های واقعی loopback و گواهی مورد اعتماد محلی برای DoT استفاده می‌کنند. تست migration ارتقا/بازگشت با حفظ مصرف کاربر و `alembic check` هم اجرا شده است. این شواهد، پذیرش VPS یا اینترنت ایران نیستند. پروفایل‌های PostgreSQL/MySQL از migration و SQLAlchemy سازگار استفاده می‌کنند؛ اجرای runtime آنها در این محیط هنوز انجام نشده است.

مبنای پاسارگارد `5eb8628cfe6db233ed2a6bbaf53f0ed497e797f9`، مبنای کد Donino Panel `cdad7417e58f212cc7b453089a8dbf6cdba9ef9c` و snapshot کاتالوگ در فایل provenance ثبت شده‌اند. الگوریتم سیاست و کاتالوگ از پروژه خود کاربر اقتباس شده‌اند؛ دیتابیس، lifecycle، API، quota transaction و UI برای معماری پاسارگارد نوشته شده‌اند. مجوز پروژه AGPL-3.0 و مجوز داده کاتالوگ MIT همراه فایل‌ها حفظ شده است.

## بسته‌بندی فورک

لینک مخزن و بررسی نسخه در داشبورد به همین فورک متصل شده‌اند. اعلان نسخه، دستور updater پروژه بالادستی را پیشنهاد نمی‌دهد. فایل Compose نیز image بالادستی را اجرا نمی‌کند؛ image محلی همین checkout را می‌سازد. معماری Dockerfile موجود، دارایی‌های ازپیش‌ساخته داشبورد را مصرف می‌کند، بنابراین پیش از build محلی:

```sh
cd dashboard
bun install --frozen-lockfile
bun run build
cd ..
docker compose up -d --build
# فقط در صورت فعال‌بودن DNS_ENABLED و تنظیم درست resolver/DB:
docker compose --profile dns up -d
```

سرویس `dns` در profile اختیاری از همان image، دیتابیس و `.env` پنل استفاده می‌کند. گواهی و کلید DoT باید از مسیرهای volume موجود و با دسترسی کاربر سرویس در دسترس باشند؛ مسیر دلخواه فایل روی میزبان خودکار داخل کانتینر ظاهر نمی‌شود. build کامل image در این مرحله اجرا نشده است؛ بررسی Python، frontend و Compose جای آزمون نصب کانتینر نیست.

نتیجه بررسی این مرحله: **۶۲ آزمون واحد/یکپارچگی مرتبط** و **۴۷ آزمون API موجود** عبور کردند. TypeScript، build تولیدی، Ruff و `git diff --check` موفق بودند. DDL جدول‌های جدید برای PostgreSQL و MySQL نیز compile شد؛ این با اجرای زنده آنها برابر نیست. آزمون مرورگر به API واقعی و دیتابیس موقت وصل شد و ساخت حساب/سیاست، مصرف واقعی DoH تا سقف، پایان سهمیه، reset، IP، غیرفعال‌سازی، audit و ادغام DNS در قالب ساب را بررسی کرد. تم تیره و عرض موبایل هم از خود رابط بررسی شدند.
